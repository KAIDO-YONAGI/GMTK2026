# GameJam 团队协作规范

> 适用团队：2 名程序 + 1 名美术
> 当前协作模式：程序负责 Unity 工程、场景和配置；美术负责美术资产产出，通过屏幕共享参与关卡视觉确认。
> 更新日期：2026-07-21

---

## 1. 核心原则

1. **一个场景同一时间只能有一个负责人。**
2. **PersistentScene 由固定程序维护，普通玩法开发不要顺手修改。**
3. **美术不直接编辑 Unity 场景、Prefab、SO 和 Import Settings。**
4. **可复用内容用 Prefab，单场景内容可以保留为场景对象。Player 是否 Prefab 化按实际需求决定。**
5. **Additive 负责组合场景，真正避免冲突的是文件所有权。**
6. **任何 Unity 资产都必须和对应 `.meta` 文件一起提交。**
7. **`main` 分支必须保持可编译、可从 InitialScene 启动。**
8. **临近交付时停止架构重构，以修复阻断问题和完成作品为优先。**

---

## 2. 职责划分

程序 A、程序 B 只是角色名称，比赛开始时必须明确实际负责人。

| 范围 | 默认负责人 | 主要职责 |
|---|---|---|
| InitialScene、PersistentScene、StartingMenu | 程序 A | 启动链、全局管理器、UI、相机、音频监听器 |
| Player 和通用玩法系统 | 程序 A 或指定负责人 | 移动、交互、状态、公共组件 |
| Level01、Level02 等内容场景 | 程序 B 或关卡负责人 | 关卡搭建、碰撞、机关、传送、场景配置 |
| 美术资产 | 美术 | Sprite、Tile、动画帧、UI 图、特效素材等 |
| Unity 资产接入 | 指定程序 | Import Settings、切图、Prefab、Animator、材质和场景摆放 |
| 最终整合与构建 | 一名指定程序 | 合并、全流程测试、构建和提交作品 |

### 2.1 负责人制度

- 开始任务前，在群聊或任务表声明自己将修改的场景、Prefab、SO 或核心脚本。
- 其他成员需要修改同一文件时，必须先联系当前负责人。
- 负责人完成并推送后，要明确通知文件已经释放。
- 一个功能涉及多个文件时，应同时说明影响范围，不能只报功能名称。

任务声明示例：

```text
负责人：程序 B
任务：Level01 机关和终点传送
预计修改：Level01.unity、Level02SO.asset、Teleport 相关 Prefab
状态：开发中
```

## 3. 场景协作规范

### 3.1 场景所有权

- `PersistentScene.unity` 必须长期保持单一负责人。
- 每个 Level 场景在一个开发时段内只能由一名程序编辑。
- 两名程序可以分别开发不同 Level，但不能同时编辑同一个 Level。
- 如果两人需要共同开发同一关卡，应拆分为脚本或 Prefab 任务，由关卡负责人统一放入场景。
- 不通过复制出 `Level01_A`、`Level01_Final2` 等场景解决冲突。

### 3.2 编辑器中的场景状态

日常开发保持：

```text
PersistentScene：loaded
StartingMenu：unloaded
Level01：unloaded
Level02：unloaded
```

编辑内容场景时：

1. 保持 PersistentScene 已加载。
2. Additive 打开需要编辑的内容场景。
3. 完成修改并保存。
4. 将内容场景 Close 为 unload 状态，不从 Hierarchy 移除。
5. 提交前确认没有意外修改其他场景。

只有完整启动测试时，可以单独打开 Build Index 0 的 InitialScene 并进入 Play Mode。

### 3.3 内容场景边界

内容场景可以包含：

- Tilemap 和场景美术
- 地面、边界和机关碰撞
- 敌人、机关、传送门
- 关卡独有的音源和配置触发器

内容场景不应重复创建：

- Main Camera
- AudioListener
- EventSystem
- SceneChanger、TimeManager、UIManager 等全局管理器
- 第二个常驻 Player

项目运行时应保持一台启用的主相机、一个启用的 AudioListener 和一个启用的 EventSystem。

### 3.4 Additive 引用规则

- 内容场景不要依赖拖拽得到的跨场景对象引用。
- 内容场景与常驻系统通信时，优先使用现有 SO 事件或明确的运行时注册接口。
- 新增内容场景时，必须同步完成：
  - 创建或配置对应的 `GameSceneSO`
  - 加入 Build Settings
  - 配置传送入口和返回位置
  - 配置场景边界与必要 Tag
  - 从 InitialScene 执行一次完整加载测试

## 4. 美术资产交付规范

### 4.1 分工边界

美术负责：

- 视觉方案和资产制作
- 输出约定格式和尺寸的文件
- 说明资源用途、尺寸、帧顺序和特殊要求
- 通过屏幕共享确认实际显示效果

程序负责：

- 将资产导入 Unity
- 设置 PPU、Filter Mode、Compression、Pivot 和 Sprite Mode
- 创建 Prefab、Animation Clip、Animator 和材质
- 将资产放入场景并配置排序、碰撞与脚本引用

### 4.2 交付信息

每次交付至少说明：

```text
资源名称：
用途：
目标尺寸：
是否透明：
Pivot 要求：
动画帧顺序和帧率：
是新增还是替换：
```

资源命名使用稳定、可搜索的英文名称，例如：

```text
Player_Idle_01.png
Player_Run_01.png
Level01_Background.png
UI_Button_Primary.png
```

### 4.3 修改已有资源

- 语义不变的修订可以保持原文件名，便于 Unity 保留现有引用。
- 用途、尺寸结构或切图方式发生变化时，应先通知负责接入的程序。
- 不要在未沟通时直接覆盖 Tile Sheet、动画序列或 UI 图集。
- 程序不要直接修改美术源文件；需要调整时反馈给美术重新导出。
- 大型源文件是否进入 Git，由团队在比赛开始时统一决定。

### 4.4 屏幕共享确认

美术不操作场景时，至少在以下节点共同查看：

1. 首次导入后：确认清晰度、透明边缘、颜色和尺寸。
2. 首次摆入场景后：确认比例、Pivot、层级和构图。
3. 动画接入后：确认帧顺序、速度和循环方式。
4. 关卡完成后：确认整体视觉节奏和信息可读性。
5. 最终构建前：在实际目标分辨率下确认画面。

## 5. Prefab、SO 与配置资产

### 5.1 Prefab

- 多场景复用、会重复生成或结构复杂的对象优先做成 Prefab。
- 只存在于一个场景且不需要复用的对象可以直接留在场景中。
- Player 不强制 Prefab 化；只有需要复用、动态生成、角色变体或减少 PersistentScene 修改时再转换。
- 修改 Prefab 前确认是否存在场景 Override。
- Apply Override 前检查影响范围，避免把某个关卡的临时调整应用到所有实例。
- Prefab 也属于不可多人同时编辑的 YAML 资产。

### 5.2 ScriptableObject

- 每个 SO 资产同一时间只由一人修改。
- 不复制事件 SO 来绕过引用问题，公共事件必须使用团队确认的同一资产。
- 修改序列化字段名称或类型前，先检查现有 SO 和场景引用。
- `GameSceneSO.sceneName` 应由场景资产同步，不手工制造与 Build Settings 不一致的名称。
- 当前 `SceneArtAssetsSO` 用于场景 BGM 和环境音配置；新增字段应基于游戏实际需求，不提前制作万能配置系统。

## 6. 代码协作规范

### 6.1 修改前

- 先拉取最新代码，并确认 `git status` 中有哪些本地改动。
- 阅读目标脚本以及直接调用它的脚本。
- 修改公共 API、事件参数、枚举或 SO 字段前，通知另一名程序。
- 不覆盖来源不明的本地修改，先确认负责人。

### 6.2 修改中

- 保持改动范围与任务一致，不顺手进行无关重构。
- 公共系统修改应兼容现有场景和 SO 资产。
- 玩家可见 UI 文本和 Inspector 文本使用英文。
- 代码注释使用中文，并只解释不明显的行为。
- 场景切换、暂停、输入和 UI 状态修改必须考虑相互调用。

### 6.3 修改后

- 等待 Unity 完成编译。
- 检查 Console 中的 Error。
- 验证受影响的最短流程。
- 检查 `git diff`，确认没有自动保存的无关场景或 ProjectSettings。
- 只提交本任务相关文件。

## 7. Git 规范

### 7.1 提交规则

- `main` 保持可运行；较大功能使用短期分支，完成验证后再合并。
- 禁止强制推送覆盖其他成员提交。
- 不提交 `Library`、`Temp`、`Logs`、IDE 缓存和本地构建产物。
- `.unity`、`.prefab`、`.asset`、图片和音频必须连同 `.meta` 一起提交。
- 移动或重命名 Unity 资产时在 Unity Project 窗口中操作，避免 GUID 丢失。
- 不使用 `git add .` 无检查提交整个工作区。

提交信息沿用当前项目风格：

```text
feat(gameplay): 添加关卡机关
feat(art): 接入玩家移动动画
fix(scene): 修复传送重复触发
fix(ui): 修复暂停菜单状态
docs(team): 更新协作规范
```

### 7.2 拉取与推送顺序

开始工作：

1. 保存并处理自己的本地修改。
2. 拉取远端最新提交。
3. 确认目标场景或资产没有被其他人占用。
4. 再打开 Unity 开始编辑。

结束工作：

1. 保存场景和资产。
2. 等待 Unity 编译完成。
3. 完成最短流程测试。
4. 检查 `git status` 和 `git diff`。
5. 提交并推送。
6. 通知团队修改范围和验证结果。

### 7.3 冲突处理

脚本冲突：

- 逐段理解双方修改后再合并。
- 合并后重新编译并测试调用链。

Scene、Prefab、SO 冲突：

- 不盲目选择 Accept Ours 或 Accept Theirs。
- 由文件负责人选择一个完整版本作为基础。
- 在 Unity 中重新补做另一方需要的修改。
- 不熟悉 Unity YAML 时不要直接手工拼接文件。

`.meta` 冲突：

- 优先保留已被场景和资产引用的 GUID。
- 不删除 `.meta` 后让 Unity 随意重新生成。
- 无法判断时由整合负责人处理。

二进制资源冲突：

- 由该资源负责人决定保留版本。
- Git 无法可靠合并图片、音频和多数美术源文件。

当前仓库没有 `.gitattributes` 或 UnityYAMLMerge 驱动，因此不能依赖 Git 自动处理 Unity 序列化资产冲突，场景和资产所有权是主要保障。

## 8. 测试与整合

### 8.1 每次提交前

- [ ] Unity 编译完成，Console 无 Error
- [ ] 本次修改对应的功能可以运行
- [ ] 没有 Missing Script 或丢失引用
- [ ] 没有误改其他人的 Scene、Prefab 或 SO
- [ ] 新增资产包含 `.meta`
- [ ] 新场景已经加入 Build Settings
- [ ] 提交内容不包含 Library、Temp 或本地构建

### 8.2 每日整合测试

从 InitialScene 执行：

1. InitialScene 加载 PersistentScene。
2. 进入 StartingMenu。
3. 从菜单进入 Level01。
4. 测试移动、机关、ESC 暂停和恢复。
5. 通过 Teleport 切换到 Level02。
6. 测试返回、重试或主菜单流程。
7. 确认切场后 `Time.timeScale` 恢复为 1。
8. 确认只有一台启用相机、一个 AudioListener 和一个 EventSystem。
9. 确认非 Player Collider 不会触发 Teleport。

### 8.3 最终构建前

- 暂停新增功能和非必要场景编辑。
- 指定一名整合负责人执行最后合并。
- 按 Build Settings 顺序检查全部场景。
- 使用目标平台和目标分辨率进行构建测试。
- 在另一台电脑或干净目录运行一次构建结果。
- 确认最终包、封面、截图、说明和成员信息齐全。

## 10. 最短执行版

时间紧张时，至少遵守以下规则：

1. 修改 Scene、Prefab、SO 前先报备。
2. 同一场景同一时间只允许一人编辑。
3. 美术交资产，程序负责 Unity 接入。
4. PersistentScene 只由固定负责人修改。
5. 所有资产连同 `.meta` 提交。
6. 提交前确认 Unity 无编译错误。
7. 每天从 InitialScene 完整运行一次。
8. 最终构建前冻结场景修改，由一人统一整合。
